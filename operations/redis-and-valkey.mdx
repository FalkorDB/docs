FalkorDB is a module that loads into a server speaking the Redis protocol
(RESP). It supports two servers:

- **[Valkey](https://valkey.io/)**, the open source (BSD-licensed) fork of Redis
  maintained under the Linux Foundation. The default FalkorDB 6.2 images use
  Valkey 9.2.
- **[Redis](https://redis.io/)** 8.0.0 or later for FalkorDB 6.2. The
  Redis-based FalkorDB 6.2 images bundle Redis 8.10.2.

The `GRAPH.*` commands, Cypher support, client libraries, and FalkorDB
configuration parameters are the same on both servers. Clients connect on port
`6379` either way, so application code does not change when you switch servers.

## Choosing a server

Both servers run FalkorDB with the same feature set. Things that differ:

- **Licensing.** Valkey is BSD-licensed. Check the Redis license that applies to
  the Redis version you deploy.
- **Server options.** Each server has options the other does not. A server
  refuses to start on an option it does not recognize.
- **Persistence files.** Valkey cannot load RDB save files written by Redis 7.4
  and later without migration. See [Moving a data volume from Redis to
  Valkey](#moving-a-data-volume-from-redis-to-valkey).

## Docker images

Each FalkorDB image ships one server, Valkey or Redis. Both
`falkordb/falkordb` and `falkordb/falkordb-server` offer these tags:

| Tag | Server |
| --- | --- |
| `latest` | Valkey 9.2 (FalkorDB 6.2) |
| `latest-redis` | Redis 8.10.2 (FalkorDB 6.2) |
| `6.0.4`, `v4.x` | Redis (older releases) |

This guide assumes the 6.2 tags are published on both image repositories before
the docs are deployed. The image-label procedure below confirms only the server
name and server version, not the FalkorDB release. Confirm the FalkorDB 6.2
release using its release notes or an explicit 6.2 image tag.

<Warning>
  Before using a Valkey image with an existing Redis volume, check for
  incompatible RDB files and data. See [Moving a data volume from Redis to
  Valkey](#moving-a-data-volume-from-redis-to-valkey).
</Warning>

### Check which server an image runs

Replace `<tag>` with the image tag, then pull and inspect it:

```bash
docker pull falkordb/falkordb-server:<tag>
docker image inspect -f '{{index .Config.Labels "com.falkordb.server.name"}} {{index .Config.Labels "com.falkordb.server.version"}}' falkordb/falkordb-server:<tag>
docker pull falkordb/falkordb:<tag>
docker image inspect -f '{{index .Config.Labels "com.falkordb.server.name"}} {{index .Config.Labels "com.falkordb.server.version"}}' falkordb/falkordb:<tag>
```

The output is `valkey <version>` or `redis <version>`. Images built before the
labels existed print `<no value>`; check the release documentation or the
running server instead.

On a running server, check `server_name` and `valkey_version` in `INFO server`
to identify Valkey; Redis reports `redis_version`. `MODULE LIST` shows the
loaded FalkorDB module.

### Running a Valkey or Redis image

```bash
# Valkey
docker run -p 6379:6379 -it --rm falkordb/falkordb-server:latest

# Redis
docker run -p 6379:6379 -it --rm falkordb/falkordb-server:latest-redis
```

For production, pin the chosen image to a tested release tag or image digest.

### Server arguments: `VALKEY_ARGS` and `REDIS_ARGS`

Pass server options with `VALKEY_ARGS` on a Valkey image and `REDIS_ARGS` on a
Redis image. If the variable for the image's own server is unset, empty, or only
whitespace, the image uses the other one, so an existing `REDIS_ARGS` setting
keeps working on a Valkey image. The two variables are never combined.

```bash
docker run -p 6379:6379 -it \
  -e VALKEY_ARGS="--requirepass yourpassword --appendonly yes" \
  -e FALKORDB_ARGS="THREAD_COUNT 4" \
  --rm falkordb/falkordb-server:latest
```

<Note>
  Options that only one server understands make the other refuse to start.
  Remove Redis-only options from `REDIS_ARGS` before running it on a Valkey
  image, or set `VALKEY_ARGS` explicitly.
</Note>

`FALKORDB_ARGS` configures the FalkorDB module and works the same on both
servers. See [Configuration](/getting-started/configuration).

The `redis-cli` command is available in both images, so health checks such as
`redis-cli ping` work unchanged. Valkey images also include `valkey-cli`.

## Self-hosting without Docker

Load the FalkorDB module into either server with `--loadmodule` or the
`loadmodule` configuration directive. Use a FalkorDB 6.2 module for Valkey;
the 6.0.4 release requires Redis.

<CodeGroup>

```bash Valkey
valkey-server --loadmodule /path/to/falkordb.so
```

```bash Redis
redis-server --loadmodule /path/to/falkordb.so
```

</CodeGroup>

Module configuration parameters follow the module path the same way on both
servers, for example `--loadmodule /path/to/falkordb.so THREAD_COUNT 4`. For
production, use the server version bundled with the official image of the same
FalkorDB build, reported by the `com.falkordb.server.version` image label.

## Moving a data volume from Redis to Valkey

Valkey cannot normally load RDB files (version 12 and later) written by Redis
7.4 and later. Earlier FalkorDB images ran Redis 8, so their volumes may contain
these files. A command-based AOF can be replayed without converting its format,
but it may contain data Valkey cannot read, and a Redis RDB file left alongside
it can still prevent startup. Check the [migration guide](https://github.com/FalkorDB/FalkorDB/blob/main/docs/valkey-migration.md)
before switching servers.

A Valkey image checks the data directory before Valkey starts. If it finds
Redis RDB files of version 12 or later, including AOF base RDB files, the
container stops, prints the file names, and leaves the volume untouched. You
then have two options:

- **Keep the data on Redis.** Continue using the original Redis image, or
  verify upgrade compatibility before using `latest-redis`.
- **Migrate to Valkey.** In summary:
  1. Back up the volume and stop application writes until migration is complete.
  2. On the Redis image, disable query-statistics collection with
     `GRAPH.CONFIG SET CMD_INFO no`, then delete FalkorDB's
     `telemetry{<graph>}` query-statistics streams. If you keep other data,
     delete or convert data Valkey cannot read, including other streams and
     hashes with field expiry. Delete a telemetry key only if its `TYPE` is
     `stream`; leave keys of other types untouched. Run `SAVE`. If AOF is
     enabled, first wait for any existing rewrite to finish by checking that
     `aof_rewrite_in_progress` and `aof_rewrite_scheduled` are both `0` in
     `INFO persistence`. Then run `BGREWRITEAOF` on Redis and wait until both
     fields are again `0` and `aof_last_bgrewrite_status` is `ok` before
     stopping Redis.
  3. Stop and remove the Redis container without deleting the volume. Start the
     Valkey image on that volume with `-e FALKORDB_REDIS_MIGRATION=1`, keeping
     the existing persistence settings, such as `--appendonly yes` when AOF
     is enabled.
  4. Verify your graphs with `GRAPH.LIST` and a query, then run `SAVE`. If AOF
     is enabled, run `BGREWRITEAOF` and confirm Valkey accepted the command.
     Wait until `aof_rewrite_in_progress` and `aof_rewrite_scheduled` in
     `INFO persistence` are both `0`, then confirm
     `aof_last_bgrewrite_status` is `ok`. If the rewrite fails, keep the
     migration container running and writes paused while you retry. Do not
     remove migration mode or restart without it until the rewrite succeeds.
     If the volume cannot be recovered in place, stop the Valkey container,
     restore the step 1 backup to a clean volume, and verify it using the
     original Redis image before resuming writes.
  5. Stop and remove the migration container, then start the Valkey image again
     without `FALKORDB_REDIS_MIGRATION`, retaining the persistence settings.
     While application writes are still paused, wait for the container to
     accept connections and verify `GRAPH.LIST` and a graph query before
     resuming writes.

Follow the full, step-by-step procedure in
[Moving a data volume from Redis to Valkey](https://github.com/FalkorDB/FalkorDB/blob/main/docs/valkey-migration.md)
before migrating production data. Query statistics start again from empty after
the migration.

<Warning>
  Graph encoding compatibility does not make Redis and Valkey persistence files
  interchangeable, and moving back from Valkey to Redis is not covered by this
  migration. Keep the pre-migration backup and review [Upgrades, Downgrades, and
  Compatibility](/operations/upgrades-downgrades-compatibility) before changing
  the server used with an existing volume.
</Warning>

## Frequently Asked Questions

<AccordionGroup>
  <Accordion title="Does FalkorDB support Valkey?">
    Yes. FalkorDB 6.2 runs as a module on both Valkey and Redis 8.0.0 or later, with the same commands, Cypher support, and configuration parameters.
  </Accordion>
  <Accordion title="Which server does the latest Docker image use?">
    FalkorDB 6.2's `latest` image uses Valkey 9.2. Use `latest-redis` to run Redis 8.10.2. Older images, including `6.0.4` and `4.x` releases, run Redis.
  </Accordion>
  <Accordion title="Do I need to change my application or client library to use Valkey?">
    No. Valkey speaks the same RESP protocol, so FalkorDB client libraries work without changes. Redis and Valkey clients can also send FalkorDB commands if they support custom commands.
  </Accordion>
  <Accordion title="Can I keep using REDIS_ARGS on a Valkey image?">
    Yes, if `VALKEY_ARGS` is unset, empty, or only whitespace. The image falls back to `REDIS_ARGS`. Options that Valkey does not recognize prevent it from starting, so remove Redis-only options or set `VALKEY_ARGS` instead.
  </Accordion>
  <Accordion title="Why does my Valkey container refuse to start on an existing volume?">
    Check the container logs: the volume may hold RDB files written by Redis 7.4 or later. Run a Redis image on that volume, or follow [Moving a data volume from Redis to Valkey](#moving-a-data-volume-from-redis-to-valkey).
  </Accordion>
</AccordionGroup>
